# 서버 운영 런북

현재: Vercel 프론트, Render API, Neon PostgreSQL. EC2 SSH/Compose는 이전 운영 방식입니다.

## 빠른 진단

| 증상 | 확인 |
| --- | --- |
| Render 시작 실패 | GOOGLE_CREDENTIALS_URI와 Secret File, DB 접속, Flyway 로그 |
| 로그인 진입 안 됨 | VITE_API_BASE_URL, Render 휴면, /oauth2/authorization/google |
| Google 콜백 오류 | OAuth 승인 URI, 서버 로그의 원인, DB 스키마 |
| exchange 403 | Origin과 CORS_ALLOWED_ORIGINS 정확한 일치, Vercel 인증 rewrite |
| refresh 401 | 만료/소비/폐기된 Refresh, 새 코드 배포 후 재로그인 |
| refresh 5xx | 서버/프록시 문제. 프론트는 자동으로 로그인 데이터를 지우지 않음 |
| NoResourceFoundException | 없는 경로 요청. 새 버전은 404로 응답하며 / 및 /healthz는 상태 JSON 제공 |
| Places 조회 실패 | event=places_failed의 HTTP 코드, API New 활성화와 키 제한 |
| 로컬 API_KEY_IP_ADDRESS_BLOCKED | 개발 키/IP 제한 준비. Render Outbound 범위는 따로 등록 |
| 생성 429 | 앱 일일 한도, 관리자 설정, 진행 중 예약 확인 |
| 생성 409 | 같은 ID의 입력 변경, 이미 진행 중, 만료/경합 |
| 생성 502/503/504 | event=ai_failed의 stage, category, rootType, http, providerStatus, reason, quota, trace 확인 |
| 편집 409 | 목적지 ID가 없는 구버전 일정. 새 조건으로 재생성 |
| 삭제 후 쿼터 유지 | 정상: 일정 데이터와 성공 사용량 장부 분리 |

AI 로그는 모델명·소요 시간·토큰 합계/실패 상태만 기록하며 프롬프트/토큰 원문은 기록하지 않습니다. 품질 검사 로그는 오류 규칙을 남깁니다. 서비스 계정 JSON, API 키, 쿠키, 로그인 코드를 로그로 수집하지 않습니다.

## 배포 후 검증

- 최신 프론트/백엔드 커밋이 같은 회차인지 확인합니다.
- 새로 로그인하여 OAuth 완료 URL에 accessToken/refreshToken이 없는지 확인합니다.
- 인증 exchange 응답에 Access만 있고 Refresh는 HttpOnly/Secure 쿠키인지 확인합니다.
- 1일 선택형 여행을 만들고 장소 ID·출처·한국어 설명·시간표를 직접 대조합니다.
- 같은 요청 ID 재전송은 같은 planId, 생성 실패는 사용량 미차감인지 확인합니다.
- 모든 날짜 편집과 저장·새로고침·삭제를 확인합니다. 타 사용자 일정 접근은 404여야 합니다.
- 관리자 초기화는 기본 3회로 충전되며 진행 중 예약은 제외하지 않습니다.
- Free 휴면 후 기동 시간, 메모리, API 사용량을 관찰합니다.

## 복구 원칙

DB 백업 없이 데이터 볼륨/테이블을 삭제하지 않습니다. Flyway checksum 오류를 파일 수정이나 이력 삭제로 감추지 않습니다. 키 제한을 전부 해제하여 장애를 우회하지 않습니다. 제한된 개발 키와 Render Outbound 허용 범위를 구분합니다.

자세한 설정은 [배포 가이드](RENDER_DEPLOYMENT.md), 현재 한계는 [아키텍처](아키텍처.md), 검증 기록은 [선택형 전환](선택형_일정_전환.md)을 따릅니다.
## AI 연결/429 장애 구분

- event=ai_start의 stage=maps_grounding/schedule와 timeoutMs로 실제 진행 단계를 확인합니다.
- category=TIMEOUT은 HTTP 대기 초과, NETWORK는 네트워크 예외, AUTH_REFRESH는 서비스 계정 토큰 갱신 실패입니다. INVALID_RESPONSE는 응답 해석 실패입니다.
- provider HTTP 401/403과 명시적 quota=true는 즉시 종료합니다. 429라는 이유만으로 크레딧 소진이라고 판단하지 않습니다.
- 일시적 429/503만 최대 2회 재시도합니다. 긴 Retry-After/RetryInfo나 재시도 시간 여유 초과 시 무한 대기하지 않습니다.
- event=maps_grounding_unavailable fallback=places_api는 Grounding 대신 Places로 확인한 후보를 사용했다는 뜻입니다. 검증을 생략한 것이 아닙니다.
- 실패 시 저장/사용량 확정 없이 예약을 해제하며 프론트도 완료 후 쿼터를 재조회합니다.
- trace로 같은 AI 호출을 연결합니다. 프롬프트·오류 원문·토큰·키는 로그에 남기지 않습니다.
- 직접 Google 호출 성공은 Render의 설정/네트워크와 전체 여행 생성 성공의 증거가 아닙니다. 배포 후 동일 조건으로 다시 확인해야 합니다.

## 인증 프록시와 느린 서버 시작

- POST /api/auth/refresh가 502이면 AI 로그가 아니라 인증/프록시 경로를 확인합니다.
- event=auth_start / event=auth_end의 path·trace·status·elapsedMs로 백엔드 도착 여부와 처리 결과를 대조합니다. 응답 헤더 X-Compass-Request-Id로 같은 요청을 찾을 수 있습니다. 인증 비밀 값은 기록하지 않습니다.
- 백엔드 로그가 없으면 최신 시간 범위를 먼저 확인하고, Vercel 프록시에서 백엔드에 도달하기 전 실패했는지 확인합니다. 로그 부재만으로 원인을 확정하지 않습니다.
- 2026-11-06 사용자 제공 로그에서는 애플리케이션 시작에 약 143초가 걸렸습니다. Render Free 휴면/기동 지연과 프록시 502의 연관성은 가능성이며 확정 원인이 아닙니다.
- 새 버전 배포 후 백엔드 /healthz를 직접 열어 status=UP 응답을 확인하고 재로그인하여 즉시 생성해 봅니다. 이는 기동 지연을 분리하는 진단 절차이며 상시 가동 보장이 아닙니다.
- 누락 경로는 404로 분리하고 실제 미처리 예외에는 HTTP 메서드와 경로(쿼리 제외)를 기록합니다. 기본 주소의 누락 경로 로그와 인증/AI 장애를 혼동하지 않습니다.
